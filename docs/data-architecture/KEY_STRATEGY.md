# Dirty Data to OLAP — Key Strategy

## Key taxonomy

| Category | Meaning | Architectural restriction |
|---|---|---|
| Physical source key | Declared PK or source-local row identifier in a table/file context. | Identifies a source record in its source scope; not automatically cross-source. |
| Declared business key | Domain-asserted identifier with explicit entity/source/time scope. | Requires a scoped domain assertion; may not be unique in every physical snapshot. |
| Candidate key | Measured hypothesis about uniqueness, nullability or reference behavior. | Remains a candidate with evidence and violation rates until accepted by policy/review. |
| Canonical identity | Project-owned identity reference for a canonical entity instance. | Must not be copied from one source key or cluster ID by convenience. |
| Canonical surrogate ID | Stable project-owned identifier used to refer to a canonical instance independently of source keys. | Requires accepted identity decision and source-record mappings. |
| Analytical surrogate key | Target-model identifier for a dimension row. | Is not a business key or canonical identity; generated by later analytical implementation. |
| Degenerate business identifier | Event/business identifier retained on a fact without a separate dimension when justified. | Requires explicit scope and lineage; does not replace fact grain. |
| Source record reference | Traceable pointer to a source record in a specific snapshot. | Must survive transformations and remain distinct from canonical and analytical IDs. |

## Identity rules

- A physical source key identifies a record only within its declared context.
- A source PK is not automatically a business key across systems.
- A candidate key is evidence, not truth.
- A canonical ID requires accepted entity scope, linkage decision, provenance and conflict/review state.
- `cluster_id != canonical_entity_id` unless a later explicit identity decision establishes the mapping.
- An analytical surrogate key is a dimensional implementation identifier, not a source or canonical identity.
- Mutable descriptive values cannot become identity merely because they are convenient.

## Benchmark use

Customer, Product and Branch may receive canonical identities after benchmark-labelled linkage decisions. Order, OrderLine and Payment are event identities with domain grain semantics; generic entity-resolution clustering must not be applied to them without a later explicit contract. The benchmark's physical line-sequence and payment-event key remain unresolved until generator/source specifications exist.
